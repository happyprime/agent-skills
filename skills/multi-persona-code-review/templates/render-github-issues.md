# GitHub-issues renderer

Generates a bash script that creates one GitHub issue per finding via `gh issue create`, with idempotency, dry-run support, and a label-creation helper.

## When invoked

Inputs:

- A run directory (default: most recent run under `${PROJECT_ROOT}/.reviews/`).
- An `owner/repo` target. If the user didn't provide one, ask. Don't assume the current working directory's git remote — users often want to file on a different repo.
- Optional flags from the user: `--dry-run` (print, don't execute), `--run` (execute the script after generating).

Outputs:

- `${RUN_DIR}/create-issues.sh` — the generated script.
- `${RUN_DIR}/create-issues.log` — log of what was filed (URLs, skipped duplicates, errors), populated when the script runs.

## What to read

- `${RUN_DIR}/findings/*.md` — every final finding.
- `summary.md` — only to extract the project name for issue context.

Do not file issues for entries in `nice-to-have.md`, `decisions-needed.md`, or `needs-debate.md`.

## Per-issue contract

Each issue produced has:

### Title

`[{ID}] {title}` — e.g., `[CRIT-001] Unauthenticated REST endpoint allows deleting any post`.

The bracketed ID is the idempotency key. The script searches existing issues for the substring `[{ID}]` and skips if a match is found.

### Body

The full finding markdown **minus the YAML frontmatter**, with a small metadata table inserted at the top of the body before `## Problem`:

```markdown
| Field | Value |
|---|---|
| **Severity** | critical |
| **Category** | security |
| **Confidence** | high |
| **Effort** | small |
| **Reviewers** | security-engineer, wordpress-developer |
| **Files** | `includes/rest/class-items-controller.php:78-92` |

---
```

The remaining body (`## Problem` through `## Synthesis notes`) is included verbatim. Don't reformat code blocks — `gh issue create --body-file` handles them.

### Labels

Compose from:

- Severity: one of `severity:critical`, `severity:high`, `severity:medium`, `severity:low`, `severity:info`.
- Category: `category:<category>` (e.g., `category:security`).
- Effort: `effort:<effort>` (e.g., `effort:small`).
- Plus any labels in the finding's `labels:` frontmatter array.

If `blocks_release: true` is set in frontmatter, also add `blocks-release`.

### Optional assignee and milestone

- If the finding has `assignee_hint:` and the user supplied `--respect-assignee-hints`, add `--assignee <hint>`.
- The user can pass a single `--milestone <name>` flag to apply to all issues; not per-finding.

## Script structure

The generated `create-issues.sh` looks like this (template — fill in per run):

```bash
#!/usr/bin/env bash
set -euo pipefail

# Generated by multi-persona-code-review on <DATE>
# Run directory: <RUN_DIR>
# Target repo: <OWNER/REPO>

REPO="<OWNER/REPO>"
DRY_RUN="${DRY_RUN:-0}"
LOG="<RUN_DIR>/create-issues.log"

log() { echo "$@" | tee -a "$LOG"; }

# --- Verify gh is available and authenticated ---
command -v gh >/dev/null 2>&1 || { echo "gh CLI not installed" >&2; exit 1; }
gh auth status >/dev/null 2>&1 || { echo "gh CLI not authenticated. Run: gh auth login" >&2; exit 1; }

# --- Ensure labels exist (idempotent) ---
ensure_label() {
  local name="$1" color="$2" desc="$3"
  if ! gh label list --repo "$REPO" --search "$name" --json name --jq '.[].name' | grep -qx "$name"; then
    if [ "$DRY_RUN" = "1" ]; then
      log "DRY-RUN: would create label $name ($color)"
    else
      gh label create "$name" --repo "$REPO" --color "$color" --description "$desc" 2>/dev/null || true
      log "Created label: $name"
    fi
  fi
}

# Severity labels (color-coded to match HTML report)
ensure_label "severity:critical" "b91c1c" "Critical severity"
ensure_label "severity:high"     "c2410c" "High severity"
ensure_label "severity:medium"   "b45309" "Medium severity"
ensure_label "severity:low"      "1d4ed8" "Low severity"
ensure_label "severity:info"     "4b5563" "Informational"

# Category labels
ensure_label "category:security"      "d73a4a" "Security finding"
ensure_label "category:performance"   "fbca04" "Performance finding"
ensure_label "category:bug"           "ee0701" "Bug"
ensure_label "category:ux"            "0e8a16" "UX issue"
ensure_label "category:accessibility" "5319e7" "Accessibility issue"
ensure_label "category:code-quality"  "c5def5" "Code quality"
ensure_label "category:architecture"  "1d76db" "Architecture"
ensure_label "category:operations"    "0052cc" "Operational concern"
ensure_label "category:testability"   "bfd4f2" "Testability"

# Effort labels
ensure_label "effort:trivial"    "c5def5" "< 1 hour"
ensure_label "effort:small"      "c5def5" "< 1 day"
ensure_label "effort:medium"     "c5def5" "1–3 days"
ensure_label "effort:large"      "fef2c0" "3 days–2 weeks"
ensure_label "effort:very-large" "fef2c0" "> 2 weeks"

ensure_label "blocks-release" "b60205" "Should block the next release"

# --- File issues ---
file_issue() {
  local id="$1" title="$2" body_file="$3" labels="$4"
  # Idempotency: skip if an issue with [ID] in the title already exists.
  if gh issue list --repo "$REPO" --state all --search "[$id] in:title" --json title --jq '.[].title' | grep -qF "[$id]"; then
    log "SKIP: $id — already filed."
    return 0
  fi
  if [ "$DRY_RUN" = "1" ]; then
    log "DRY-RUN: would create [$id] $title (labels: $labels)"
    return 0
  fi
  local url
  url="$(gh issue create --repo "$REPO" --title "$title" --body-file "$body_file" --label "$labels")"
  log "Filed: $id — $url"
}

# --- Per-finding calls below ---
# (One block per finding, generated from findings/*.md)

# Example shape:
# file_issue "CRIT-001" \
#   "[CRIT-001] Unauthenticated REST endpoint allows deleting any post" \
#   "<RUN_DIR>/.tmp-issue-bodies/CRIT-001.md" \
#   "severity:critical,category:security,effort:small,blocks-release"
```

The generator writes one `file_issue` call per finding, and writes the per-issue body to `${RUN_DIR}/.tmp-issue-bodies/{ID}.md` so that `--body-file` is used (avoids quoting hell with code fences and backticks).

## Behavior

- **Idempotent.** Re-running the script files only new findings; previously-filed ones are detected by the `[ID]` substring in existing issue titles.
- **Dry-run.** Setting `DRY_RUN=1` prints what would happen without filing or creating labels.
- **Order.** File in severity order — critical first, info last — so the most important issues appear first in the repo.
- **Rate limits.** GitHub allows ~150 issue creations per hour for unauthenticated calls and significantly more for authenticated. Don't artificially throttle; the script's serial calls are slow enough.
- **Failure handling.** If a single `gh issue create` fails, log and continue. The script's exit code reflects whether any failed (non-zero if so).

## Handoff to the github-issues skill

If the `github-issues` skill is installed in the user's environment, prefer handing off rather than rolling everything yourself. The github-issues skill knows how to discover existing labels, match house style, and ground references in code. Pass it:

- The repo target.
- The list of finding markdown files (under `${RUN_DIR}/findings/`).
- A note: "These are pre-classified findings from a multi-persona code review. Use the metadata in each frontmatter rather than re-classifying."

If `github-issues` is not installed, use the script approach above.

## Reporting back

After generating (and optionally executing) the script, report to the user:

- Path to `create-issues.sh`.
- Whether it was executed or just generated.
- Count of issues filed / skipped / failed (if executed).
- Path to `create-issues.log`.
